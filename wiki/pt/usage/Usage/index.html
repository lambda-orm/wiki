Uso

Esta página mostra diferentes formas de usar o λORM com o mesmo domínio de exemplo (Northwind) em diferentes infraestruturas: uma única fonte, várias fontes, CQRS com vários stages e um cliente Node.js conectado a um Data Gateway.

Para manter os esquemas curtos, as propriedades, chaves, índices e relações das entidades, assim como os mapeamentos, foram omitidos. Os esquemas completos estão nos labs.

Fonte única

Esquema

O domínio tem cinco entidades: Categories, Customers, Products e Orders, onde Orders é uma entidade composta formada pelos pedidos e seus detalhes (Orders.details). A infraestrutura tem um único stage com uma única fonte, Ordering, um banco de dados MySQL que usa o mapeamento padrão.

domain:  
  entities:
  - name: Categories
  - name: Customers
  - name: Products
  - name: Orders
  - name: Orders.details
infrastructure:
  mappings:
  - name: default
  sources:
    - name: Ordering
      mapping: default
      dialect: MySQL
      connection: ${CNN_MYSQL}
  stages:
  - name: default
    sources:
      - name: Ordering

Consulta

A consulta obtém um pedido de um cliente, com seus detalhes. Ela é escrita como uma expressão lambda e executada com a biblioteca @lambdaorm/lib.

import { orm } from '@lambdaorm/lib'
import { Orders } from './northwind/domain/model'

(async () => {
  try {
    // initialize the ORM with the schema file
    await orm.init('./lambdaORM.yaml')
    // query
    const query = (customerId: string) => Orders
      .filter(p => p.customerId == customerId)
      .include(p => [
        p.customer.map(p => p.name),
        p.details
          .include(p => p.product
            .include(p => p.category.map(p => p.name))
            .map(p => p.name))
          .map(p => [p.quantity, p.unitPrice])
      ])
      .page(1, 1)
    // execute the query
    const result = await orm.execute(query, { customerId: 'CENTC' })
    console.log(JSON.stringify(result, null, 2))
  } catch (error: any) {
    console.error(error)
  } finally {
    await orm.end()
  }
})()

Várias fontes

Esquema

Neste caso, as entidades do domínio são armazenadas em fontes diferentes:

  • Categories e Products são armazenadas na fonte Catalog, um banco de dados MySQL que usa o mapeamento padrão.
  • Customers é armazenada na fonte Crm, um banco de dados PostgreSQL que usa o mapeamento padrão.
  • Orders é armazenada na fonte Ordering, um banco de dados MongoDB que usa o mapeamento mongoDb.

A condition de cada fonte no stage decide quais entidades ela armazena.

domain:  
  entities:
  - name: Categories
  - name: Customers
  - name: Products
  - name: Orders
  - name: Orders.details
infrastructure:
  mappings:
  - name: default
  - name: mongoDb
    extends: default
  sources:
  - name: Catalog      
    dialect: MySQL
    mapping: default
    connection: ${CNN_MYSQL}      
  - name: Crm    
    dialect: PostgreSQL
    mapping: default
    connection: ${CNN_POSTGRES}
  - name: Ordering
    dialect: MongoDB
    mapping: mongoDb      
    connection: ${CNN_MONGODB}    
  stages:
  - name: default
    sources:
    - name: Catalog
      condition: entity.in(["Categories","Products"])
    - name: Crm
      condition: entity.in(["Address","Customers"])
    - name: Ordering
      condition: entity.in(["Orders","Orders.details"])

Consulta

Desta vez, a consulta é executada a partir da CLI. O código não muda com a infraestrutura, e o resultado é o mesmo do caso anterior, embora os dados agora venham de três bancos de dados.

lambdaorm execute -e ".env" -q "Orders.filter(p => p.customerId == customerId).include(p => [p.customer.map(p => p.name), p.details.include(p => p.product.include(p => p.category.map(p => p.name)).map(p => p.name)).map(p => [p.quantity, p.unitPrice])]).page(1,1)" -d "{\"customerId\": \"CENTC\"}"

CQRS

O CQRS (Command Query Responsibility Segregation) separa o modelo usado para escrever os dados do modelo usado para lê-los. Com o λORM, é uma questão de configuração.

Esquema

Este esquema define três stages para o mesmo domínio:

  • default: os dados são lidos das fontes Catalog, Crm e Ordering e escritos nelas.
  • insights: os dados são lidos da fonte Insights e escritos nela.
  • cqrs: os dados são lidos da fonte Insights, mas escritos nas fontes Catalog, Crm e Ordering.

Para manter Insights em sincronia com Catalog, Crm e Ordering, um listener é executado após cada insert, bulk insert, update ou delete nos stages default e cqrs, e aplica a mesma operação no stage insights.

domain:  
  entities:
  - name: Categories
  - name: Customers
  - name: Products
  - name: Orders
  - name: Orders.details
infrastructure:
  mappings:
  - name: default
  - name: mongoDb
    extends: default
  sources:
  - name: Catalog      
    dialect: MySQL
    mapping: default
    connection: ${CNN_MYSQL}      
  - name: Crm    
    dialect: PostgreSQL
    mapping: default
    connection: ${CNN_POSTGRES}
  - name: Ordering
    dialect: MongoDB
    mapping: mongoDb      
    connection: ${CNN_MONGODB}
  - name: Insights    
    dialect: PostgreSQL
    mapping: default
    connection: ${CNN_INSIGHTS}         
  stages:
  - name: default
    sources:
    - name: Catalog
      condition: entity.in(["Categories","Products"])
    - name: Crm
      condition: entity.in(["Address","Customers"])
    - name: Ordering
      condition: entity.in(["Orders","Orders.details"])
  - name: insights
    sources:
    - name: Insights
  - name: cqrs
    sources:
    - name: Insights
      condition: action == "select"
    - name: Catalog
      condition: entity.in(["Categories","Products"])
    - name: Crm
      condition: entity.in(["Address","Customers"])
    - name: Ordering
      condition: entity.in(["Orders","Orders.details"])
application:
  listeners:
    - name: syncInsights
      on: [insert, bulkInsert, update, delete ]
      condition: options.stage.in("default","cqrs")
      after: orm.execute(query,data,{stage:"insights"})

Consulta

Desta vez, a consulta é executada em um Data Gateway que serve este esquema, por meio da sua API REST:

curl -X POST "http://localhost:8080/execute?format=beautiful" -H "X-Api-Key: $KEY" -H "Content-Type: application/json" -d '{"query": "Orders.filter(p=>p.customerId==customerId).include(p=>[p.details.include(p=>p.product.map(p=>p.name)).map(p=>{subTotal:p.quantity*p.unitPrice}),p.customer.map(p=>p.name)]).sort(p=>p.orderDate).page(1,1)", "data": {"customerId": "CENTC"}, "options": {"stage": "default"}}'

CQRS com Kafka

Quando o esquema é servido por um Data Gateway, a sincronização pode passar pelo Kafka: o listener publica os inserts, updates e deletes dos stages default e cqrs em um tópico com queue.send, e um consumidor os aplica no stage insights. A fila é configurada em infrastructure.queue (config é a configuração do kafkajs); veja execute-queued.

Esquema

...
infrastructure:
  ...
  queue: 
    config: $QUEUE_CONFIG
    consumers:
      - name: syncInsights
        config:
          groupId: group1
        subscribe:
          topic: insights-sync
          fromBeginning: true
        execute: orm.execute(message.query,message.data, {stage:"insights"})    
application:
  listeners:
    - name: syncInsights
      on: [insert, bulkInsert, update, delete ]
      condition: options.stage.in("default","cqrs")
      after: queue.send("insights-sync",[{query,data}])

Cliente Node.js

Esquema

Com um cliente, o esquema local define apenas o domínio, a URL do Data Gateway e os caminhos onde lambdaorm build -l client-node gera o modelo; as fontes e suas conexões pertencem ao esquema servido pelo Data Gateway. lambdaorm init -u <url> cria este esquema com o domínio lido do gateway.

domain:  
  entities:
  - name: Categories
  - name: Customers
  - name: Products
  - name: Orders
  - name: Orders.details
infrastructure:
  service:
    url: http://localhost:8080
  paths:
    src: src
    domain: northwind/domain

Consulta

Desta vez, a consulta é executada por meio do cliente Node.js (@lambdaorm/client), que se conecta a um Data Gateway, e é escrita como uma string. Aqui o gateway serve um único esquema na raiz, então a URL é a do gateway; caso contrário, ela inclui a rota do esquema (por exemplo http://localhost:8080/northwind).

import { orm } from '@lambdaorm/client'
import fs from 'fs'
import path from 'path'

(async () => {
  try {
    await orm.init('http://localhost:8080', { headers: { 'X-Api-Key': process.env.BACKEND_KEY } })
    // test the connection
    console.log(await orm.general.ping())
    // import the data of the data.json file
    const content = fs.readFileSync(path.join(__dirname, '../data.json'), 'utf-8')
    await orm.stage.import('default', JSON.parse(content))
    // query as a string
    const query = `Orders
      .filter(p => p.customerId == customerId)
      .include(p => [
        p.customer.map(p => p.name),
        p.details
          .include(p => p.product
            .include(p => p.category.map(p => p.name))
            .map(p => p.name))
          .map(p => [p.quantity, p.unitPrice])
      ])`
    // get the execution plan
    const plan = await orm.plan(query, { stage: 'default' })
    console.log(JSON.stringify(plan, null, 2))
    // execute the query
    const result = await orm.execute(query, { customerId: 'CENTC' }, { stage: 'default' })
    console.log(JSON.stringify(result, null, 2))
  } catch (error: any) {
    console.error(error)
  } finally {
    await orm.end()
  }
})()

Considerações

  • Tanto com @lambdaorm/lib quanto com @lambdaorm/client, as consultas podem ser escritas como expressões lambda ou como strings.
  • As consultas são escritas sobre o modelo do domínio e não dependem da infraestrutura. Um projeto pode começar com uma infraestrutura simples e alterá-la depois sem mexer no código.
  • Os ambientes de desenvolvimento, teste e produção podem ter infraestruturas diferentes (stages) com o mesmo código.

Muitos outros casos de uso podem ser resolvidos configurando o esquema e escrevendo consultas. Explore os labs e o restante desta documentação.
