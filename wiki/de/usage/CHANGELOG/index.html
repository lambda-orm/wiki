    3.2.0¶

    Minor Changes¶

    • 7c18bef: - A filter by a field of a relation whose entity lives in another source works (L15): QuoteLines.filter(p => p.deviceModel.name == name) first queries DeviceModels on its source and then filters QuoteLines with in(p.deviceModelId, …). Each comparison is solved on its own (&&, ||, ! keep their meaning); the other side must be a value (a clear error otherwise) and only one level of relation is supported.
    • PostgreSQL: in(p.x, list) / p.x.in(list) with the list in a variable works — the parameter was typed as its elements and the array was sent as a Postgres array literal (L33).
    • 38e7d3b: New orm.executeScript(script, data, options): evaluates a 3xpr script whose orm.execute(query, data, options) calls all run in one transaction, also across sources. The script can use variables, if, for, for … in, throw, try/catch and return; it commits when it ends and rolls back and rejects when anything fails (a query, a function or a throw). It works on a copy of data, cannot read environment variables, and its orm.execute calls without a stage run on the script's stage. Returns the value of the last statement (or of return).
    const quoteId = await orm.executeScript(
  `
  orm.execute("Quotes.insert()", { id: quoteId, accountId: accountId, status: "draft" });
  for (line in lines) {
    orm.execute("QuoteLines.insert()", { id: line.id, quoteId: quoteId, deviceModelId: line.modelId, quantity: line.qty });
  }
  orm.execute("Accounts.update(p => ({ lastQuoteAt: now() })).filter(p => p.id == accountId)", { accountId: accountId });
  quoteId
`,
  { quoteId, accountId, lines }
);
    • 3f3e1cc: Listeners (application.listeners) are awaited one after the other and run in the sentence's transaction: their orm.execute calls use the same connections, an error in before prevents the sentence, an error in after fails it, and a rollback undoes what they wrote. A sentence with listeners that runs on its own opens a transaction for itself and its listeners. They used to run detached (forEach(async …)): execute could return before them, their errors escaped as uncaught exceptions and they wrote outside the transaction — L10.

    New listener option transactional: false (base ListenerConfig): the listener runs outside the transaction, and what it writes is kept even if the sentence's transaction rolls back.

    • c2be59f: push compares the model with the databases (as fetch reads them), not with orm_state — L19: a new environment or a CI runner without the last push's orm_state no longer gets CREATE TABLE for tables that exist. Tables missing in the database are created with their keys, FKs and indexes; in existing tables, missing columns are added (ADD COLUMN, L27), columns with another type, length or nullability are altered, and a property mapping with previousMapping: <old column> renames the column (ALTER TABLE … RENAME COLUMN, L20; SqlServer sp_rename). Nothing that exists only in the database is dropped (stage.fetch() reports it). orm_state is still written by push as a record.
    • d16b60a: stage.push().sentencesBySource(): the DDL grouped per source (one script per database). cli: lambdaorm push -o <dir> writes one script per source that changes, <stage>.<source>.sql (deterministic names, to rename into a versioned migration); -o without a folder prints the DDL grouped by source — L19.
    • e961817: update().include(p => p.children) on a composite relation saves the aggregate: the children sent are inserted or updated (upsert by primary key, with the parent's key), and the parent's children that were not sent are deleted. Children absent from the data are not touched. It used to update only the existing children that were sent — L17. Supported where upsert is (PostgreSQL, MySQL, MariaDB); SqlServer, Oracle and SQLjs report it as not supported yet (MongoDB keeps composite children embedded). An explicit include(p => p.children.update(…)) keeps updating only.

    • 8b8f470: Stage commands:

    • push/DDL: a stage's last source without condition is a catch-all, as in DML: it gets only the entities no other source took (it used to receive every entity) — L25.

    • fetch/pull on PostgreSQL work with reserved words as column names (order): the metadata query quoted the column twice — L6, L21.
    • stage.fetch() reports the drift: per mapping, the entities that differ from the model (present in one side only, different columns, types, lengths, required, primary key), each with its differences; no entities when in step. stage.read() returns the databases' mappings as fetch did (pull uses it) — L22.

    • cli: lambdaorm fetch exits with code 1 when there are differences (for CI). fetch, pull, schema, introspect and incorporate load the --envfile they declared (it was ignored).

    • 907074b: Transactions:

    • orm.transaction now waits for the transaction: it resolves after the commit and rejects with the callback's error after the rollback (the error used to escape as an uncaught exception and the promise resolved undefined) — L26. If the rollback itself fails, the callback's error is still the one reported.

    • Everything executed inside orm.transaction joins it, also when it doesn't go through tr: orm.execute, repositories, the orm.execute function of an expression. It runs on the transaction's connections (one per source), so a rollback undoes it — L31. A nested orm.transaction joins the outer one, a query with include no longer opens a second transaction, and an execution on another stage inside a transaction fails with a clear error. Each Orm instance keeps its own transaction context.

    • 7c8edd7: Types and values:

    • New property type json (L1): objects and lists are written as JSON and come back as objects and lists. Column type: PostgreSQL JSONB, MySQL/MariaDB JSON, SqlServer NVARCHAR(MAX), Oracle CLOB, others TEXT. A list is no longer sent as a Postgres array literal.

    • The mapping's dbType reaches the DDL when a table or column is created or altered (it was used in one place only) — e.g. dbType: timestamptz(3) (L1, L2).
    • PostgreSQL writes dateTime with milliseconds and the offset (yyyy-MM-dd HH:mm:ss.SSSZZ): milliseconds are kept and a timestamptz column stores the exact instant; timestamp columns keep storing the local time (L2).
    • '', 0 and false parameters are values: only undefined becomes NULL (an empty string used to be written as NULL, and so were 0 and false) — L3. (The "" literal needs 3xpr 5.1.1.)

    • A string property without length is no longer given length 80 in the model: PostgreSQL creates TEXT, the other dialects keep VARCHAR(80) — L24. On PostgreSQL, the next push of an existing model widens those columns to TEXT.

    • de140f3: update answers the number of affected rows (as delete does, and as the repositories' update(): Promise<number> always declared); it answered { data: <parameters> }. Lets callers detect "not found" (0) and optimistic-lock conflicts (filter(p => p.id == id && p.version == version) → 0) — L4. SQLjs update/delete now return the modified rows too.

    • 6319468: Entity.upsert(): insert, or update the row with the same primary key, in one sentence — PostgreSQL INSERT … ON CONFLICT (pk) DO UPDATE SET c = EXCLUDED.c, MySQL/MariaDB ON DUPLICATE KEY UPDATE c = VALUES(c) (other dialects: a clear "not supported" error). Written like an insert (upsert(), upsert(entity), upsert({ … })); answers the data like insert — L18. It used to fail with function: upsert not found.
