Usage

This page shows different ways of using λORM with the same example domain (Northwind) on different infrastructures: a single source, several sources, CQRS with several stages, and a Node.js client connected to a Data Gateway.

To keep the schemas short, the properties, keys, indexes and relations of the entities, as well as the mappings, are omitted. The complete schemas are in the labs.

Single source

Schema

The domain has five entities: Categories, Customers, Products and Orders, where Orders is a composite entity made of the orders and their details (Orders.details). The infrastructure has a single stage with a single source, Ordering, a MySQL database that uses the default mapping.

domain:  
  entities:
  - name: Categories
  - name: Customers
  - name: Products
  - name: Orders
  - name: Orders.details
infrastructure:
  mappings:
  - name: default
  sources:
    - name: Ordering
      mapping: default
      dialect: MySQL
      connection: ${CNN_MYSQL}
  stages:
  - name: default
    sources:
      - name: Ordering

Query

The query gets an order of a customer, with its details. It is written as a lambda expression and run with the @lambdaorm/lib library.

import { orm } from '@lambdaorm/lib'
import { Orders } from './northwind/domain/model'

(async () => {
  try {
    // initialize the ORM with the schema file
    await orm.init('./lambdaORM.yaml')
    // query
    const query = (customerId: string) => Orders
      .filter(p => p.customerId == customerId)
      .include(p => [
        p.customer.map(p => p.name),
        p.details
          .include(p => p.product
            .include(p => p.category.map(p => p.name))
            .map(p => p.name))
          .map(p => [p.quantity, p.unitPrice])
      ])
      .page(1, 1)
    // execute the query
    const result = await orm.execute(query, { customerId: 'CENTC' })
    console.log(JSON.stringify(result, null, 2))
  } catch (error: any) {
    console.error(error)
  } finally {
    await orm.end()
  }
})()

Multiple sources

Schema

In this case the entities of the domain are stored in different sources:

  • Categories and Products are stored in the Catalog source, a MySQL database that uses the default mapping.
  • Customers is stored in the Crm source, a PostgreSQL database that uses the default mapping.
  • Orders is stored in the Ordering source, a MongoDB database that uses the mongoDb mapping.

The condition of each source in the stage decides which entities it stores.

domain:  
  entities:
  - name: Categories
  - name: Customers
  - name: Products
  - name: Orders
  - name: Orders.details
infrastructure:
  mappings:
  - name: default
  - name: mongoDb
    extends: default
  sources:
  - name: Catalog      
    dialect: MySQL
    mapping: default
    connection: ${CNN_MYSQL}      
  - name: Crm    
    dialect: PostgreSQL
    mapping: default
    connection: ${CNN_POSTGRES}
  - name: Ordering
    dialect: MongoDB
    mapping: mongoDb      
    connection: ${CNN_MONGODB}    
  stages:
  - name: default
    sources:
    - name: Catalog
      condition: entity.in(["Categories","Products"])
    - name: Crm
      condition: entity.in(["Address","Customers"])
    - name: Ordering
      condition: entity.in(["Orders","Orders.details"])

Query

This time the query is run from the CLI. The code does not change with the infrastructure, and the result is the same as in the previous case, although the data now comes from three databases.

lambdaorm execute -e ".env" -q "Orders.filter(p => p.customerId == customerId).include(p => [p.customer.map(p => p.name), p.details.include(p => p.product.include(p => p.category.map(p => p.name)).map(p => p.name)).map(p => [p.quantity, p.unitPrice])]).page(1,1)" -d "{\"customerId\": \"CENTC\"}"

CQRS

CQRS (Command Query Responsibility Segregation) separates the model used to write data from the model used to read it. With λORM it is a matter of configuration.

Schema

This schema defines three stages for the same domain:

  • default: data is read from and written to the Catalog, Crm and Ordering sources.
  • insights: data is read from and written to the Insights source.
  • cqrs: data is read from the Insights source but written to the Catalog, Crm and Ordering sources.

To keep Insights in step with Catalog, Crm and Ordering, a listener runs after each insert, bulk insert, update or delete on the default and cqrs stages, and applies the same operation on the insights stage.

domain:  
  entities:
  - name: Categories
  - name: Customers
  - name: Products
  - name: Orders
  - name: Orders.details
infrastructure:
  mappings:
  - name: default
  - name: mongoDb
    extends: default
  sources:
  - name: Catalog      
    dialect: MySQL
    mapping: default
    connection: ${CNN_MYSQL}      
  - name: Crm    
    dialect: PostgreSQL
    mapping: default
    connection: ${CNN_POSTGRES}
  - name: Ordering
    dialect: MongoDB
    mapping: mongoDb      
    connection: ${CNN_MONGODB}
  - name: Insights    
    dialect: PostgreSQL
    mapping: default
    connection: ${CNN_INSIGHTS}         
  stages:
  - name: default
    sources:
    - name: Catalog
      condition: entity.in(["Categories","Products"])
    - name: Crm
      condition: entity.in(["Address","Customers"])
    - name: Ordering
      condition: entity.in(["Orders","Orders.details"])
  - name: insights
    sources:
    - name: Insights
  - name: cqrs
    sources:
    - name: Insights
      condition: action == "select"
    - name: Catalog
      condition: entity.in(["Categories","Products"])
    - name: Crm
      condition: entity.in(["Address","Customers"])
    - name: Ordering
      condition: entity.in(["Orders","Orders.details"])
application:
  listeners:
    - name: syncInsights
      on: [insert, bulkInsert, update, delete ]
      condition: options.stage.in("default","cqrs")
      after: orm.execute(query,data,{stage:"insights"})

Query

This time the query is run on a Data Gateway that serves this schema, through its REST API:

curl -X POST "http://localhost:8080/execute?format=beautiful" -H "X-Api-Key: $KEY" -H "Content-Type: application/json" -d '{"query": "Orders.filter(p=>p.customerId==customerId).include(p=>[p.details.include(p=>p.product.map(p=>p.name)).map(p=>{subTotal:p.quantity*p.unitPrice}),p.customer.map(p=>p.name)]).sort(p=>p.orderDate).page(1,1)", "data": {"customerId": "CENTC"}, "options": {"stage": "default"}}'

CQRS with Kafka

When the schema is served by a Data Gateway, the synchronization can go through Kafka instead: the listener publishes the inserts, updates and deletes of the default and cqrs stages to a topic with queue.send, and a consumer applies them on the insights stage. The queue is configured in infrastructure.queue (config is the kafkajs configuration); see execute-queued.

Schema

...
infrastructure:
  ...
  queue: 
    config: $QUEUE_CONFIG
    consumers:
      - name: syncInsights
        config:
          groupId: group1
        subscribe:
          topic: insights-sync
          fromBeginning: true
        execute: orm.execute(message.query,message.data, {stage:"insights"})    
application:
  listeners:
    - name: syncInsights
      on: [insert, bulkInsert, update, delete ]
      condition: options.stage.in("default","cqrs")
      after: queue.send("insights-sync",[{query,data}])

Node.js client

Schema

With a client, the local schema only defines the domain, the URL of the Data Gateway and the paths where lambdaorm build -l client-node generates the model; the sources and their connections belong to the schema served by the Data Gateway. lambdaorm init -u <url> creates this schema with the domain read from the gateway.

domain:  
  entities:
  - name: Categories
  - name: Customers
  - name: Products
  - name: Orders
  - name: Orders.details
infrastructure:
  service:
    url: http://localhost:8080
  paths:
    src: src
    domain: northwind/domain

Query

This time the query runs through the Node.js client (@lambdaorm/client), which connects to a Data Gateway, and it is written as a string. Here the gateway serves a single schema at the root, so the URL is the gateway's; otherwise it includes the route of the schema (for example http://localhost:8080/northwind).

import { orm } from '@lambdaorm/client'
import fs from 'fs'
import path from 'path'

(async () => {
  try {
    await orm.init('http://localhost:8080', { headers: { 'X-Api-Key': process.env.BACKEND_KEY } })
    // test the connection
    console.log(await orm.general.ping())
    // import the data of the data.json file
    const content = fs.readFileSync(path.join(__dirname, '../data.json'), 'utf-8')
    await orm.stage.import('default', JSON.parse(content))
    // query as a string
    const query = `Orders
      .filter(p => p.customerId == customerId)
      .include(p => [
        p.customer.map(p => p.name),
        p.details
          .include(p => p.product
            .include(p => p.category.map(p => p.name))
            .map(p => p.name))
          .map(p => [p.quantity, p.unitPrice])
      ])`
    // get the execution plan
    const plan = await orm.plan(query, { stage: 'default' })
    console.log(JSON.stringify(plan, null, 2))
    // execute the query
    const result = await orm.execute(query, { customerId: 'CENTC' }, { stage: 'default' })
    console.log(JSON.stringify(result, null, 2))
  } catch (error: any) {
    console.error(error)
  } finally {
    await orm.end()
  }
})()

Considerations

  • With both @lambdaorm/lib and @lambdaorm/client, queries can be written as lambda expressions or as strings.
  • Queries are written against the domain model and do not depend on the infrastructure. A project can start with a simple infrastructure and change it later without touching the code.
  • Development, test and production environments can have different infrastructures (stages) with the same code.

Many other use cases can be solved by configuring the schema and writing queries. Explore the labs and the rest of this documentation.
