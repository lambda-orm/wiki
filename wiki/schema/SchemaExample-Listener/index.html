Listener on Schema

This page explains listeners: expressions that λORM runs before or after a query, or when it fails. They are defined in application.listeners (see Listener).

  • on: the categories of query that trigger the listener: select, insert, upsert, update and delete. A bulk insert belongs to the insert category, and a merge to the upsert category.
  • condition: an expression that decides whether the listener runs.
  • before, after and error: the expressions to run before the query, after it, or when it fails.
  • transactional: whether the listener runs inside the query's transaction (default true).

How listeners run

  • before, after and error run one after the other and are awaited: orm.execute returns when they have finished. An error in before prevents the sentence; an error in after fails it (the error listeners run first).
  • They run in the sentence's transaction: the orm.execute calls of a listener use the same connections, and a rollback undoes what they wrote. A sentence with listeners that runs on its own opens a transaction for the sentence and its listeners, so both are all or nothing.
  • A listener's orm.execute can name another stage ({ stage: "insights" }): it joins the same transaction (since @lambdaorm/lib 3.3.0).
  • transactional: false runs a listener outside the transaction: what it writes is kept even if the transaction rolls back (for example, an audit log).

In this example, touchInstallation updates the installation of each inserted file in the same transaction, and audit writes an audit log that is kept even if the transaction rolls back:

application:
  listeners:
    - name: touchInstallation
      on: [insert]
      condition: entity == "InstallationFiles"
      after: >-
        orm.execute("Installations.update(p => ({ lastEventAt: at })).filter(p => p.id == id)",
          { id: data.installationId, at: data.uploadedAt })
    - name: audit
      on: [insert, update, delete]
      transactional: false
      after: orm.execute("AuditLogs.insert()", { entity: entity, action: action })

Arguments

The arguments available in condition, before, after and error:

Parameter Description
query The query expression that was executed
data The data that was sent when the expression was executed
options The options that were sent when the expression was executed
result It is only available in the after event and contains the result of the expression execution
action The action that was executed (select, insert, bulkInsert, update, upsert, merge, bulkMerge, delete, bulkDelete)
type The type of sentence that was executed (dql, dml)
category The category of the sentence that was executed (select, insert, update, delete, upsert)
sentence The sentence that was executed
dialect The dialect of the source where the sentence was executed
source The source where the sentence was executed
entity The entity that was affected by the sentence
error It is only available in the error event and contains the error that occurred

Listener Example

This example declares a listener that copies the data to the insights stage (CQRS pattern). When records are inserted, updated or deleted on the default or cqrs stage, the listener runs. Its after expression executes the same query, with the same data, on the insights stage, in the same transaction as the original query: if the write in insights fails, the original one is rolled back too.

Part of the schema where the listener is defined:

...
application:
  listeners:
    - name: syncInsights
      on: [insert, update, delete]
      condition: options.stage.in("default","cqrs")
      after: orm.execute(query,data,{stage:"insights"})

Complete schema:

The default stage spreads the entities over MySQL, PostgreSQL and MongoDB, the insights stage stores everything in another PostgreSQL database, and the cqrs stage reads from insights and writes to the sources of default.
