# Exemplo de entidade composta {#composite-example}

Esta página mostra uma entidade composta, `Orders.details`, armazenada no MongoDB em um stage e no PostgreSQL em outro, e como a mesma consulta retorna o mesmo resultado em ambos.

Um ponto no nome de uma entidade define uma [entidade composta](SchemaDefinition-Composite.md): `Orders.details` é uma entidade composta de `Orders`.

Se a fonte for NoSQL, os detalhes são armazenados dentro do pedido, em uma única coleção; se a fonte for relacional, eles são armazenados em tabelas separadas.
No domínio, eles são tratados da mesma forma, qualquer que seja o tipo de fonte, de modo que o modelo não depende da tecnologia de persistência.

## Entidade composta {#composite-entity}

Neste exemplo, `Orders.details` é uma entidade composta de `Orders`. Sua relação `order`, com `target: details`, cria a relação composta `details` em `Orders`.

**Parte do esquema onde a entidade composta é definida:**

```yaml
domain:  
  entities:
...  
  - name: Orders
    primaryKey: [id]
    indexes:
    - name: orderDate
      fields: [orderDate]
    properties:
    - name: id
      type: integer
      required: true
      autoIncrement: true
    - name: customerId
      required: true
      length: 5
    - name: orderDate
      type: dateTime 
  - name: Orders.details
    primaryKey: [orderId, productId]
    properties:
    - name: orderId
      required: true
      type: integer
    - name: productId
      required: true
      type: integer
    - name: unitPrice
      type: decimal
    - name: quantity
      type: decimal
    relations:
    - name: order
      from: orderId
      entity: Orders
      to: id
      target: details
...
```

      - name: Orders

          - name: id
            mapping: _id
  sources:
  - name: Catalog      
    dialect: MySQL
    mapping: default

## Entidade composta em fontes diferentes {#composite-entity-in-different-sources}

Este exemplo mostra como uma entidade composta é armazenada em fontes diferentes.
No stage `default`, `Orders` e `Orders.details` são armazenadas no MongoDB; no stage `insights`, são armazenadas no PostgreSQL.

**Parte do esquema onde os stages são configurados:**

```yaml
...
  stages:
  - name: default
    sources:
    - name: Catalog
      condition: entity.in(["Categories","Products"])
    - name: Crm
      condition: entity.in(["Address","Customers"])
    - name: Ordering
      condition: entity.in(["Orders","Orders.details"])
  - name: insights
    sources:
    - name: Insights
...
```

## Consultas {#queries}

A mesma consulta, executada em cada stage, retorna os mesmos pedidos com seus detalhes (apenas o formato das datas depende do mecanismo de banco de dados).

### Consulta no stage default {#query-on-default-stage}

```sh
lambdaorm execute -e ".env" -s default -q "Orders.filter(p => p.customerId == customerId).include(p => [p.customer.map(p => p.name), p.details.include(p => p.product.include(p => p.category.map(p => p.name)).map(p => p.name)).map(p => [p.quantity, p.unitPrice])]).sort(p=> p.id).page(1,1)" -d "{\"customerId\": \"HANAR\"}"
```
