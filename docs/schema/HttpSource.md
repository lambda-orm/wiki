# A REST API as a source

The dialect **`Http`** makes the entities of a REST API part of the domain: relations, `include`, validations, views
and observability, as with a database. Use it when some of the data lives behind a service (billing, a CRM, another
team's API) and you want to query and relate it with the same expressions as the tables of your databases.

```yaml
infrastructure:
  mappings:
    - name: main
    - name: billing
      entities:
        - name: Invoices
          mapping: /invoices                       # its route: the REST convention
          http: { filters: [status, customerId] }  # what the API filters by as parameters
          properties:
            - { name: id, autoIncrement: true }    # the API generates the key
            - { name: customerId, mapping: customer_id }   # the name of the field in the API
  sources:
    - name: billing
      dialect: Http
      mapping: billing
      connection: { url: https://api.billing.com, headers: { Authorization: 'Bearer ${BILLING_TOKEN}' }, timeout: 10000 }
    - name: db
      dialect: PostgreSQL
      mapping: main
      connection: ${CNN_POSTGRES}
  stages:
    - name: default
      sources:
        - { name: billing, condition: 'entity == "Invoices"' }
        - { name: db }
```

## The route of an entity

The `mapping` of the entity is its route, and the convention is `GET /invoices`, `GET /invoices/{id}`,
`POST /invoices`, `PATCH /invoices/{id}` and `DELETE /invoices/{id}`. The key `http` of the entity mapping declares
what differs:

| Key | Description | Example |
| --- | --- | --- |
| `list` | Another route for a list | `'GET /v2/invoices/search'` |
| `get`, `insert`, `update`, `delete` | Another route for that action | `'PUT /invoices/{id}'` |
| `items` | Where the rows of a list are in the answer (by default the answer itself, its `data` or its `items`) | `'data.items'` |
| `filters` | The properties the API filters by as query parameters; the rest of the filter runs in memory | `[status, customerId]` |

The key is generated by the API: declare it `autoIncrement`, and `insert` returns the key the API answered.

## What each sentence does

| Sentence | On the API | In memory |
| --- | --- | --- |
| A filter by its key | `GET /invoices/{id}` (404: no rows) | — |
| A list | `GET /invoices?status=…` (the properties of `filters`) | the rest of the filter, map, grouping, `having`, sort, page |
| An include of it | `GET /invoices/{id}` for each key | — |
| `insert` | `POST`, with the names of the API | — |
| `update` / `delete` by key | `PATCH` / `DELETE` `/invoices/{id}` | — |

An `update` or `delete` without the key in its filter is an error. `push`, `drop` and `truncate` do nothing on an
API.

## Authentication

The simplest one is a header of the connection, with the secret in an environment variable (`headers` above). The
connection can also get a token with OAuth2 and forward headers from the context of who runs the query:

```yaml
connection:
  url: https://api.billing.com
  auth:                                  # OAuth2 client credentials
    type: oauth2
    tokenUrl: https://auth.billing.com/oauth/token
    clientId: ${BILLING_CLIENT_ID}
    clientSecret: ${BILLING_CLIENT_SECRET}
    scope: invoices                      # and audience, if the API asks for it
  forward:                               # header: a 3xpr expression on the context of the query
    X-User: context.user
    X-Tenant: upper(context.tenant)
```

- **`auth`:** λORM asks for the token (`grant_type=client_credentials`), sends it as `Authorization: Bearer …` and
  keeps it, shared by the connections, until a minute before it expires (`expires_in`; without it, an hour). If the
  API answers 401, it asks for another token and repeats the request once.
- **`forward`:** headers taken from the [context](Context.md) of who runs the query (`options.context`), so a gateway
  can pass on to the API the identity or the token of the user that called it. Without the value, or if the
  expression fails, the header is not sent. It goes with every request: reads, writes (also the ones deferred to the
  commit) and `bulkInsert`.

## Transactions

An API has no rollback. Inside a transaction its writes wait for the commit, which the Http source does **before**
the databases: if something fails earlier, they are not sent; if the API fails, the databases roll back. An `insert`
whose key the API generates is sent at once, because its answer is needed. The only gap left is an API that answers
well followed by a database whose commit fails; for a full guarantee, use the
[outbox](SchemaDefinition.md#outbox).
